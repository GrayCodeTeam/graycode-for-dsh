# ADR-0003：Staged diff 决策门（P3D）——DSH 原生 diff/approval 不满足延迟审阅语义

- 状态：accepted（决策门完成；staged-diff service 已立项但**本期不实现**）
- 依据：PLAN_V2.md §P3D / §6 能力矩阵「延迟接受/拒绝文件改动」/ §6.4 / §7.3；ADR-0001（版本锁定与扩展面约束）；ADR-0002（会话事件持久化 GAP 与 sidecar 模式）
- 探针：`packages/plugin/tests/spike/staged-diff.spec.ts`（8 用例，全部真实运行通过）

> 探针基线：DSH `0.1.0-rc.6`（npm `next` dist-tag，与参考基线 `47f9438` 同源发布）。以下结论均来自对已安装包公开类型声明/行为的阅读与可运行探针，引用「包名 + 公开符号」，不含源码文件路径；与 [PROGRESS.md](./PROGRESS.md) Phase 0 P0-08 与 P3D 条目互见。

## 1. 调研结论（公开符号）

### 1.1 diff 只有「展示词汇」，没有「门」语义 — VERIFIED

| 事实 | 公开符号 |
| --- | --- |
| 单文件变更的展示形状：`oldText` 为新建/覆写时为 `null`（call 时拿不到旧内容），`newText` 为变更后内容 | `@deepseek-ai/dsh-tools` `FileDiff` |
| 待执行调用的 diff 卡片：由**调用参数**推导，声明在 `presentCall` | `DiffCallView`（`card: 'diff'`）/ `ToolDefinition.presentCall` |
| 已完成的 diff 卡片：展示「已应用」的变更（result-time 上下文化 hunk），声明在 `presentResult` | `DiffResultView` / `ToolDefinition.presentResult` |
| 工具私有展示载荷随 `tool/result` 事件持久化、可随会话日志回放（`dsh-tool-fs` 即把 result-time 上下文 diff 放这里） | `@deepseek-ai/dsh-session` `SessionEventMap['tool/result'].meta` |

结论：`presentCall`/`presentResult` 是纯函数展示意图（文档明确「Pure and side-effect-free」），`presentResult` 执行时**文件已经落盘**；展示层没有任何「接受/拒绝后决定是否落盘」的钩子。

### 1.2 approval 是「写前、按整次调用」的接缝 — VERIFIED（服务本体未安装）

| 事实 | 公开符号 |
| --- | --- |
| 分发前门：监听器返回 `allow` / `deny` / `ask`；`ask` 交给 approval 服务，否则退化为 deny | `@deepseek-ai/dsh-tools` `'tools/pre-execute'` waterfall、`PreToolDecision` |
| 审批接缝以 `ctx.get('approval')` 消费；`request({ agent, toolName, callId, reason?, signal })` 返回 `'allowed-once' \| 'rejected' \| 'cancelled' \| 'unavailable'` | `ToolRuntime.serviceAsk`（dsh-tools）；服务定义属 `@deepseek-ai/dsh-user-approval`（dsh-tools 的 peerDependency） |
| 本工作区未安装 `dsh-user-approval` → 无服务时 `ask` 稳定退化为 deny（探针 1a 实测 `requires approval (not yet supported)`） | — |
| 审批粒度 = 一次工具调用（pre-dispatch），**不是文件粒度**；`PreToolDecision` 文档明确「输入改写被排除」（不能把写调用改道/暂存） | `PreToolDecision`、`ToolDefinition` 文档 |

### 1.3 fs 写路径立即提交，无 staging、无审批钩子 — VERIFIED

| 事实 | 公开符号 |
| --- | --- |
| 写/编辑是原子 create-or-replace，立即生效，返回 `before`/`after` 供消费者事后计算 diff | `@deepseek-ai/dsh-fs` `FileSystem.writeText` / `editText`、`FsWriteOutcome` |
| 写路径唯一 waterfall 是陈旧防护意图（`createIfAbsent` / `replaceIfVersion`），不是审批或暂存 | `'fs/write-intent'` / `'fs/edit-intent'`、`FsWriteIntent` |
| 观察记录是同步 emit（记录型，不能改写流程） | `'fs/observed'` |
| 本地后端无沙箱/审批（`sandboxMode` 为 `undefined`），审批只存在于工具层 | `@deepseek-ai/dsh-fs-local` `LocalFileSystem` |

### 1.4 执行后没有回滚路径 — VERIFIED

- `tools/post-execute` 的 `block` 只把已执行结果变成错误反馈，**不会回滚工具已做的 fs 写**（探针 2b 实测：block 后两个文件仍在盘上）。
- `tools/execute` 环绕包装只允许替换 `exec.signal`；`tools/pre-execute` 明确不提供输入改写。→ 插件无法在公开流水线上把 DSH 文件工具的写「延迟到用户接受」。

### 1.5 会话持久化与「待审状态」无关 — VERIFIED（backend 缺失）

- `SessionPersistence` 是抽象 Service Definition（`create`/`append`/`load`/`prepare`/`inspect`/`list`…）；本环境未挂载任何具体 backend。
- 无 backend 时 `AgentRegistry.resume` 经 agent-loop 工厂抛 `cannot resume: session persistence is not configured (load a dsh-session-persistence backend)`（探针 4a 实测）。
- 即使挂载 backend，持久化的也只是**事件日志**（含 diff 展示 meta）；审批请求是进程内 request/response，不存在可持久化的「待审队列」。

### 1.6 探针可驱动性 — VERIFIED

`tests/e2e/harness.ts` 组合（LocalFileSystem → SessionStore → AgentRegistry → SystemPrompt → ToolRuntime → LlmRuntime → AgentLoop → graycode）可端到端驱动「工具写文件 → tools/pre-execute ask → ctx.approval 服务 → 写盘 → tool/result diff meta」；`ctx.provide('approval', stub)`（cordis 公开 API）可注入审批服务；根 ctx 的 `ctx.on('tools/pre-execute')` 监听器能收到全部调用（dsh-scope 只过滤带 scope 标签的监听器）。

## 2. 四场景探针结果

| 场景 | 旧 GrayCode 语义 | DSH 0.1.0-rc.6 实际行为（探针证据） | 判定 |
| --- | --- | --- | --- |
| 1 单文件接受 | 文件写入先进入待审，用户在 UI 上审阅后接受才落盘 | ask 只能**写前**放行/拒绝（allowed-once 后文件立即落盘；rejected 或缺失 approval 服务时文件不写）；写后只有展示性 diff 卡片（`tool/result.meta`），无「写后接受/拒绝已写文件」API | **GAP**（可降级为「先审后写」的写前确认，但延迟接受语义缺失） |
| 2 部分文件拒绝 | 一次修改多文件时，可只接受一个、拒绝其余 | 审批粒度 = 整次工具调用：单调用写两文件时一次 allowed-once 后两文件全部落盘，无文件级 accept/reject；post-execute `block` 只把结果转错误，**已写文件不回滚** | **GAP** |
| 3 跨工具累计 | 多个工具先后修改可累计为一批，一起审阅 | 每次调用即时落盘、各自独立审批（探针 3a：两次调用 → 两次独立 approval.request）；累计的只有会话日志（两组成对的 `tool/call`+`tool/result`，diff meta 可回放），不存在「跨调用合并待审集合」 | **GAP** |
| 4 会话重启后继续审阅 | 待审列表持久化，重启后仍在 | 无 persistence backend 时 resume 直接抛错；有 backend 也只能恢复事件日志（历史展示，探针 4b 验证 diff meta 可回放）；审批请求是进程内 request/response，待审状态无持久化载体 | **GAP** |

结论：**四个产品必需语义全部缺失**（无一项可借 DSH 原生能力满足）。

## 3. 决策

1. **实现 staged-diff service（Gray owner），本期只完成决策门，不进入实现。**
   - 依据 PLAN_V2 §P3D：任一产品必需语义缺失 → 先写 ADR 明确状态机、所有权和恢复策略后再开发。
   - D-05 结论更新：staged diff 不再是「待测项」，而是**首发必做工作包**（并入 Phase 3 排期，工作量 10–18 工程师日，见 §12）。
2. **条件采用 DSH 原生 approval**：staged-diff 的「写前确认」环节复用 `tools/pre-execute` `ask` + `ctx.approval`（allowed-once），不另造确认机制；但该环节只是前置门，不能替代延迟接受。
3. **所有权与边界**：
   - Gray owner：staged-diff domain（条目状态机、批/会话累计、拒绝与恢复策略）、Gray 写工具适配层（写工具先把内容写入 staged 区/记录意图，接受后才经 `ctx.fs` 落盘）、持久化 sidecar、Client 审阅视图（P4-06）。
   - DSH owner：`ctx.fs` 原子写（落盘与回滚依据 `FsWriteOutcome.before`）、`tools/pre-execute` approval 接缝（写前确认）、session 日志（已接受变更的历史展示）。
   - 禁止：深层 import DSH 私有源码、`as any` 绕过服务契约、在公开流水线上「假装拦截」DSH 文件工具（pre-execute 无输入改写，拦截不了）。

## 4. 状态机草案（本期不实现，仅定案）

```text
                    ┌────────────────────────── 跨工具/跨调用累计 ──────────────────────────┐
                    │                                                                        │
 tool 写请求 ──► 条目 pending ──► (用户打开审阅视图) ──► reviewing ──┬─► accepted ──► 经 ctx.fs 落盘 ──► done
                    ▲                                                └─► rejected ──► 不落盘；若与已落盘内容冲突，按恢复策略处理 ──► done
                    │
                    └──── 会话重启：sidecar JSON 重建 pending/reviewing 条目（不依赖自定义会话事件持久化，ADR-0002 §2 GAP 未关闭前一律走 sidecar）
```

- 持久模型：`<dataRoot>/staged-diff/entries.json`（原子 tmp+rename 写，与 branches sidecar 同一模式）；条目含 `id`、`workspaceId`、`sessionId`、`path`、`before`（`FsWriteOutcome.before` 或读盘快照）、`after`、`toolCallId`、`status: pending|reviewing|accepted|rejected|done`、`createdAt`、`revision`（CAS）。
- 跨工具累计：同一 workspace+session 下的 pending/reviewing 条目构成一个审阅批；批不是独立实体，是条目集合的派生视图。
- 拒绝语义：**未落盘的条目拒绝 = 什么都不写**（Gray 写工具先把内容存 staged 区，绝不提前写 workspace）；对已落盘冲突（如 checkpoint 恢复与 staged 条目重叠）→ 拒绝时按 `before` 快照补偿写回，或要求先走 checkpoint 恢复审批。
- 恢复策略：重启后按 sidecar 重建条目；`accepted` 但未落盘（崩溃窗口）的条目标记 `needs-reapply`，由人工确认后重放；不自动落盘。
- 一致性：每条目以 `revision`/CAS 更新；写盘成功后再置 `done` 并发布最终事件；不向 UI 假报完成。

## 5. 影响面

- **Phase 2 E2E 语义**：`修改单文件` / `修改多文件后取消` 场景需按 staged 语义重写验收（写入不再即时可见）。
- **P3C checkpoints**：restore 的 preview→approval→落盘链路与 staged 条目存在交集，恢复审批需与 staged-diff 拒绝/补偿策略对齐。
- **Phase 4 P4-06**：staged diff 卡片（接受/拒绝边界与回放）从「条件项」转为必做 UI 面。
- **§7.3 迁移**：旧 `diffs/` 目录（临时/延迟 diff 状态）映射到新 staged-diff 条目；未提交修改必须人工确认，绝不自动应用。
- **工具描述文案**：现有 `create_design`/`update_design` 等 Gray 写工具的 description 已写明「immediately (no user confirmation step)」，实现 staged 后需同步改写（避免对模型撒谎）。

## 8. 后果

- P3D 判定：**DSH 原生 diff/approval 不满足 GrayCode 延迟文件审阅语义（四场景全 GAP），staged-diff service 需要实现**；本期产出决策门（本 ADR + 探针），未写业务代码。
- DSH 原生能力按「条件采用」保留：写前确认走 `tools/pre-execute` + `ctx.approval`；落盘/回滚依据走 `ctx.fs`；历史展示走 session 日志。
- staged-diff 条目持久化沿用 sidecar 模式（ADR-0002 §2：第三方自定义会话事件持久化 GAP 未关闭前，不入会话日志）。
- 该能力不得成为 Phase 3 其他领域的隐式依赖（PLAN §P3D）；checkpoints/workflows 不得假定文件写入「即时可见」。
